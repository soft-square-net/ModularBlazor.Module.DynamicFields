# ModularBlazor.Module.DynamicFields

DynamicFields: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers. It defines the
**fields** that content is made of, and validates content made with them.

A field is one kind of content (a news post, a paragraph, an image, an album) as one
[schema.org](https://schema.org/CreativeWork) type, with:

- its **values** (`properties`): key, label, kind (Text, RichText, Integer, Decimal, Boolean, Date, DateTime, Url, Choice,
  Asset, Keyword, Term), required, list or single, limits, and the schema.org property it is published as;
- its **style** choices: theme tokens, optionally per breakpoint (`{ "base": "full", "md": "half" }`), never free CSS;
- the fields it may contain as **children**, with counts. Fields are reusable: an image can be a child of a post, an
  album and a reportage;
- optionally the **editor dialog** of another client module that edits it (`Module.Media/edit-image`).

Authors change a field's draft; publishing freezes it as the next numbered version, pinning each child to the child's
newest published version, so content made with a version always validates the same way. A post is a tree of content
nodes, the post itself at the root: each node names a field version and holds its `content` values and `style`.
The Contents module stores the tree; this module checks it.

## Layout

```
src/WebApi.Modules.DynamicFields.Core/             Core: FieldAggregate (field, versions, rules, JSON Schema export), ContentValidation (content trees)
src/WebApi.Modules.DynamicFields.UseCases/         use cases: one folder each, a Mediator command or query and its handler, returning an Ardalis Result
src/WebApi.Modules.DynamicFields.Infrastructure/   data: DynamicFieldsDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.DynamicFields.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/openapi/dynamicfields.json                     the module's OpenAPI document, exported from Web (see "Building")
src/WebApi.Modules.DynamicFields.Client/           typed API client, generated by NSwag from that document: a hidden client module
src/Module.DynamicFields/                          Blazor client module: the Fields page (/dynamicfields) over the API client
tests/         UnitTests (Core, UseCases; NSubstitute) and IntegrationTests (Infrastructure on SQLite)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md: layers, dependency rules, adding a feature
```

The module's id, route prefix and database schema are `dynamicfields`; its permissions are `dynamicfields.read` and
`dynamicfields.manage`.

## The API

| Method and route (under `/api/dynamicfields`) | Permission | Use case |
| --- | --- | --- |
| `GET /fields?page=&pageSize=&search=&canBeRoot=` | `dynamicfields.read` | `ListFieldsQuery`: one page by key; `canBeRoot=true`: the fields a post can be made of |
| `GET /fields/{key}` | `dynamicfields.read` | `GetFieldQuery`: the draft and the list of versions |
| `GET /fields/{key}/versions/{number}` | `dynamicfields.read` | `GetFieldVersionQuery`: a published version (0: the newest), with its content and style as JSON Schema 2020-12 |
| `POST /fields` `{ key, draft }` | `dynamicfields.manage` | `CreateFieldCommand`: 201 with the field; 409 if the key exists |
| `PUT /fields/{key}/draft` `{ version, draft }` | `dynamicfields.manage` | `EditFieldDraftCommand`: 409 if the field changed since `version` |
| `POST /fields/{key}/publish` `{ version }` | `dynamicfields.manage` | `PublishFieldCommand`: the next version; 409 if a child field is not published yet |
| `DELETE /fields/{key}?version=` | `dynamicfields.manage` | `DeleteFieldCommand`: 204; 409 once the field has been published |
| `POST /content/validate` `{ root }` | `dynamicfields.read` | `ValidateContentQuery`: `{ valid, issues: [{ path, message }] }`, paths as JSON Pointers |
| `POST /content/validate-node` `{ field, fieldVersion, content, style }` | `dynamicfields.read` | `ValidateNodeQuery`: one node's values and style (no children), the same report; 404 if the version is not published |

A broken rule in a draft (a bad key, an unknown schema.org type, a choice without options, ...) is a 409 with the rule
as its detail. Content validation checks, at every node: the field version is published; the root can be a post; the
parent allows the child, at the pinned version, within its counts; the content has exactly the field's values, of the
right kinds and within their limits; the style uses only the field's tokens and breakpoints (`base`, `sm`, `md`, `lg`,
`xl`). A tree has at most 500 nodes and 12 levels, as in the Contents module.

Every call needs a signed-in caller in a tenant (`X-Tenant` header or the token's tenant). The setting
`DynamicFields:MaxPageSize` (default 100) caps the page size; change it on the Host Modules page.

In the Blazor client, the **Fields** menu entry opens the Fields page (`/dynamicfields`): the fields a page at a time,
a search box and a "posts only" filter. A row opens the field with its versions and its draft as JSON, to save,
publish, or delete while never published. It is an admin tool until the field editor exists. It calls the API through
`DynamicFieldsClient`, so what a user may do is what the API allows; its errors (403, 409, ...) show as messages.
"Try the editor" opens the edit dialog on the newest version and shows what it returns.

### The edit dialog

`Module.DynamicFields/edit-content` is the one generic editor for a node's values and style, opened by id through
`IModuleDialogs` (any client module can open it; a field's `editorDialog` names another to use instead):

```csharp
var result = await ModuleDialogs.ShowAsync("Module.DynamicFields/edit-content",
    new { field = "block.image", version = 2, content, style }); // version, content and style are optional
if (!result.Canceled) { /* result.Data: { field, version, content, style } */ }
```

It loads the field version (the newest when none is given) and builds one control per value: text, a textarea for rich
text, number, checkbox, date, date and time, URL, a select (or checkboxes when multiple) for a choice, and a list with
Add and remove for multiple values. Style values are selects of the field's tokens; a responsive one can be set per
breakpoint. Save checks required values, then asks `POST /content/validate-node`, and shows each issue under its value.
Asset, Keyword and Term values are ids typed by hand, with a Pick button when `Module.Media/pick-asset`,
`Module.Keywords/pick-concepts` or `Module.Taxonomies/pick-terms` is installed (parameters `{ multiple, selected }`,
result `{ ids }`). Rich text is a plain textarea for now.

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.DynamicFields.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.DynamicFields.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.DynamicFields.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.DynamicFields.Web -ModuleId dynamicfields `
    -Output <this repo>/src/openapi/dynamicfields.json
```

## Installing

The server part is the build output of `WebApi.Modules.DynamicFields.Web` (`bin/<Configuration>/net10.0`: every layer
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: the tenant migrations run per tenant, the routes are mapped
under `/api/dynamicfields`.

The client parts are two assemblies, uploaded on the client's Client Modules page (`/client-modules`), the API client
first: `soft.square.net.WebApi.Modules.DynamicFields.Client.dll` (hidden; other client modules may depend on it) and
`soft.square.net.Module.DynamicFields.dll` (the Fields page). The playground builds all three for you: `playground/out/dynamicfields.zip`
and `playground/out/client/`.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.DynamicFields      this repo
```

(another location: `--property:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080,
client 5070), so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.DynamicFields.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart the `webapi` resource in the dashboard |
| `install` | The platform starts without the module, as in production; upload `playground/out/dynamicfields.zip` on http://localhost:5070/host-modules (sign in as the dev platform admin) and activate it, then the two dlls in `playground/out/client/` on http://localhost:5070/client-modules, the API client first |

In Development the platform seeds the tenants `acme` and `globex`. The playground grants the module's permissions in
`acme` to the dev accounts through `Access:DevGrants`: `acme-admin@modular.local` gets `dynamicfields.*`,
`editor@modular.local` gets `dynamicfields.read`. Their passwords are in the platform's
`WebApi.Identity.Server/appsettings.Development.json`. Sign in on http://localhost:5070 as `acme-admin@modular.local`
and open **Fields** for the Fields page; the API is browsable at http://localhost:5080/scalar.

Data stays in the Docker volume `dynamicfields-playground-data` and in `playground/.data`; delete both to start over.
