# ModularBlazor.Module.DynamicFields

DynamicFields: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers. It defines the
**fields** that content is made of, and validates content made with them.

A field is one kind of content (a news post, a paragraph, an image, an album) as one
[schema.org](https://schema.org/CreativeWork) type, with:

- its **values** (`properties`): key, label, kind (Text, RichText, Integer, Decimal, Boolean, Date, DateTime, Url, Choice,
  Asset, Keyword, Term, Lookup), required, list or single, limits, and the schema.org property it is published as; an
  Asset (a file) may say which files it takes (`accept`: `image/*`, `video/mp4`, `.pdf`, ...);
- for a field a post can be made of, optional **value groups** (`groups`: `main`, `seo`, ...): each value is in one
  (`group`; none: the first), so one group can be edited, reviewed and routed apart (the SEO section gets `seo`). Content
  still stores every value flat;
- its **style** choices: theme tokens, optionally per breakpoint (`{ "base": "full", "md": "half" }`), never free CSS;
- the fields it may contain as **children**, with counts. Fields are reusable: an image can be a child of a post, an
  album and a reportage;
- optionally the **editor dialog** of another client module that edits it (`Module.Media/edit-image`).

Authors change a field's draft; publishing freezes it as the next numbered version, pinning each child to the child's
newest published version, so content made with a version always validates the same way. A post is a tree of content
nodes, the post itself at the root: each node names a field version and holds its `content` values and `style`.
The Contents module stores the tree; this module checks it.

## Layout

```
src/WebApi.Modules.DynamicFields.Core/             Core: FieldAggregate (field, versions, rules, JSON Schema export, schema.org catalog, starter library), ContentValidation (content trees)
src/WebApi.Modules.DynamicFields.UseCases/         use cases: one folder each, a Mediator command or query and its handler, returning an Ardalis Result
src/WebApi.Modules.DynamicFields.Infrastructure/   data: DynamicFieldsDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.DynamicFields.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/openapi/dynamicfields.json                     the module's OpenAPI document, exported from Web (see "Building")
src/WebApi.Modules.DynamicFields.Client/           typed API client, generated by NSwag from that document: a hidden client module
src/Module.DynamicFields/                          Blazor client module: the Fields page, the field builder and the edit dialog, over the API client
tests/         UnitTests (Core, UseCases; NSubstitute) and IntegrationTests (Infrastructure on SQLite)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md: layers, dependency rules, adding a feature
```

The module's id, route prefix and database schema are `dynamicfields`; its permissions are `dynamicfields.read` and
`dynamicfields.manage`.

## The API

| Method and route (under `/api/dynamicfields`) | Permission | Use case |
| --- | --- | --- |
| `GET /fields?page=&pageSize=&search=&canBeRoot=` | `dynamicfields.read` | `ListFieldsQuery`: one page by key; `canBeRoot=true`: the fields a post can be made of |
| `GET /fields/{key}` | `dynamicfields.read` | `GetFieldQuery`: the draft and the list of versions |
| `GET /fields/{key}/versions/{number}` | `dynamicfields.read` | `GetFieldVersionQuery`: a published version (0: the newest), with its content and style as JSON Schema 2020-12 |
| `POST /fields` `{ key, draft }` | `dynamicfields.manage` | `CreateFieldCommand`: 201 with the field; 409 if the key exists |
| `PUT /fields/{key}/draft` `{ version, draft }` | `dynamicfields.manage` | `EditFieldDraftCommand`: 409 if the field changed since `version` |
| `POST /fields/{key}/publish` `{ version }` | `dynamicfields.manage` | `PublishFieldCommand`: the next version; 409 if a child field is not published yet, or a root field has no URL prefix or another published root field's |
| `DELETE /fields/{key}?version=` | `dynamicfields.manage` | `DeleteFieldCommand`: 204; 409 once the field has been published |
| `POST /content/validate` `{ root }` | `dynamicfields.read` | `ValidateContentQuery`: `{ valid, issues: [{ path, message }] }`, paths as JSON Pointers |
| `POST /content/validate-node` `{ field, fieldVersion, content, style }` | `dynamicfields.read` | `ValidateNodeQuery`: one node's values and style (no children), the same report; 404 if the version is not published |
| `POST /content/translations/check` `{ root, translation? }` | `dynamicfields.read` | `CheckTranslationQuery`: the tree's translatable values (`units`: node id, key, source, `sourceHash`, state) and, with an overlay, its `issues` and a `summary` of current, stale and missing |
| `POST /content/translations/apply` `{ root, translations, culture?, useStale? }` | `dynamicfields.read` | `ApplyTranslationsQuery`: the tree with its text in the reader's culture (the culture's overlay, then its parents', then the source), the `chain` used and counts |
| `POST /content/jsonld` `{ root, assets?, names?, url?, language?, draft?, placeholders? }` | `dynamicfields.read` | `BuildJsonLdQuery`: the post as schema.org JSON-LD (see "JSON-LD"), `{ jsonLd, skipped }`; 404 if the root's version is not published (and no `draft` is given) |
| `GET /catalog/schema-org` | `dynamicfields.read` | `GetSchemaOrgCatalogQuery`: the schema.org types (path, every property, suggested ones), their properties (label, suggested kind, limits) and the style presets |
| `GET /catalog/root-post-fields` | `dynamicfields.read` | `ListRootPostFieldsQuery`: the published root post fields (the post kinds) by key, `[{ key, title, description, schemaType, urlPrefix, version }]` (see "Root post fields and their URLs") |
| `GET /catalog/starter-fields` | `dynamicfields.read` | `ListStarterFieldsQuery`: the starter library, each marked `installed` when the tenant has a field with its key |
| `POST /catalog/starter-fields/install` `{ keys? }` | `dynamicfields.manage` | `InstallStarterFieldsCommand`: creates and publishes them (no keys: all) with the fields they contain; `{ installed, skipped, drafts }` |

A broken rule in a draft (a bad key, an unknown schema.org type, a choice without options, ...) is a 409 with the rule
as its detail. Content validation checks, at every node: the field version is published; the root can be a post; the
parent allows the child, at the pinned version, within its counts; the content has exactly the field's values, of the
right kinds and within their limits; the style uses only the field's tokens and breakpoints (`base`, `sm`, `md`, `lg`,
`xl`); a node id, when given, is 1 to 128 characters, not `$root`, and used **once** in the tree (translation and design
overlays key on it). A tree has at most 500 nodes and 12 levels, as in the Contents module.

Every call needs a signed-in caller in a tenant (`X-Tenant` header or the token's tenant). The setting
`DynamicFields:MaxPageSize` (default 100) caps the page size; change it on the Host Modules page.

### schema.org catalog and starter library

The builder works from a curated part of schema.org (`SchemaOrgCatalog` in Core): CreativeWork and the subtypes an
editorial site publishes (articles and news, media, pages and galleries, quotations, reviews and fact checks, how-tos
and recipes, books, ...), each with the properties search engines and AI read. Every property suggests a value kind
(an image is an Asset, keywords are Keyword concepts, a section is a Taxonomy term), a label, help and limits; every type
suggests the properties to start with. Image properties (`image`, `thumbnailUrl`) accept `image/*`, and a media type's
`contentUrl` accepts its media (`ImageObject`: `image/*`, `VideoObject`: `video/*`, `AudioObject`: `audio/*`; a plain
`MediaObject`: any file). The supported types of a field are exactly the catalog's. `StylePresets` holds
common style choices (width, alignment, spacing, tone, text size, heading level, aspect ratio, columns, layout); width,
alignment, spacing, tone, text size, aspect ratio and columns are responsive, so the designer's Mobile, Tablet and Desktop
views can set them apart.

The **starter library** (`StarterFields`) is ready-made fields built on it, with the values search engines ask for
marked required: the blocks `block.heading`, `block.text`, `block.paragraph`, `block.quote`, `block.image` (with
required alternative text), `block.video`, `block.audio`, `block.gallery` (of images), and the posts `post.article`
(URL prefix `articles`), `post.news` (`news`), `post.review` (`reviews`, a schema.org Review with what it reviews and its
rating), `post.blog` (`blog`), `post.video` (`videos`), `post.reportage` (`reportage`, a schema.org ReportageNewsArticle
with a dateline), `post.photo-story` (`photo-stories`, an Article whose pictures are in its gallery and image blocks) and
`post.other` (`posts`, an Article), which may contain any block. The posts group their values: `main` (Story) and `seo`
(Search and sharing: the summary and keywords). `post.video` is a schema.org VideoObject with the same value keys as the
other posts, published under a video's names: `headline` as `name`, `image` as `thumbnailUrl` and `datePublished` as
`uploadDate` (the three Google requires), and `section` as `genre`. It adds the video file (`video`, `video/*`),
`embedUrl`, `duration` and `transcript`, all optional. The starter panel shows these titles and descriptions in the
user's language (English or Arabic, `i18n/ar.json`); an installed field stores the English ones. A tenant installs them on demand; installed fields are
ordinary fields it can change and publish again. Installing never overwrites a key the tenant has; a parent whose child
exists unpublished is created as a draft, and so is a post whose URL prefix another published post field of the tenant
has already (pick another prefix, then publish it).

### Root post fields and their URLs

A root field (`canBeRoot`, a field a post can be made of) is a **post kind**: Article, News, Review. Each has a static URL,
`urlPrefix` on its draft and on each published version: the public route prefix of posts of that kind (`news` gives
`/news/...`). The rules (`FieldRules.CheckUrlPrefix`, checked in the domain, a 409 when broken):

- a lowercase slug path: segments of `a-z`, `0-9` and single hyphens between them, separated by `/`, with no slash at
  either end, at most 200 characters (`news`, `ar/news`, `opinion-pieces`);
- only a root field has one; publishing a root field requires it;
- unique per tenant among the root fields that are published now (`fields.PublishedUrlPrefix`, the newest published
  version's prefix; checked when publishing).

Publishing a field that is no longer a root drops its prefix. A root draft saved without one (an older client, or a field
from before prefixes) keeps the published prefix. The migration `AddUrlPrefix` gave every published root field the prefix
its key suggests (`FieldRules.SuggestUrlPrefix`: `post.article` → `articles`, `post.news` → `news`, `post.review` →
`reviews`, `post.blog` → `blog`, any other key without `post.` and with `.` as `-`), with `-{id}` added where two fields of
a tenant would share one. The suggestion has since learned `post.video` → `videos`, `post.photo-story` → `photo-stories`
and `post.other` → `posts` (`post.reportage` → `reportage` follows the general rule); the migration did not use these.

A posts module resolves a post's kind (the root field key) to its URL with `GET /catalog/root-post-fields`: one entry per
published root field, with the newest version's title, description and schema type. `GET /fields` also returns
`urlPrefix` per field (null when the field is not a published root). The field builder has a URL prefix input for root
fields, with the suggestion of its key.

### The Blazor client

The **Fields** menu entry opens the Fields page (`/dynamicfields`): the fields a page at a time, a search box, a
"posts only" filter, and the **Starter library** panel to install some or all of the starter fields. A row opens the
field in the **builder** (`/dynamicfields/build?key=block.image`; "New field" opens an empty one):

1. **What it is**: key, title, description, the schema.org type (grouped by family, with its description and path) and
   whether a post can be made of it. Picking a type for a field without values adds the type's suggested values.
2. **Values**: one row per value (label, key, kind, schema.org property, required, list, help, limits, options, and its
   group when the field has groups), to reorder or remove; below, the type's other schema.org properties to add with one
   click (filterable, suggested first), or a custom value. A post field can define its **value groups** here ("Add Story
   and SEO groups" in one click, which also moves the summary and keywords to SEO).
3. **Style**: the presets to add with one click, or a custom style; tokens, default, responsive.
4. **What it can contain**: the tenant's fields to allow as children, with minimum and maximum counts.

Beside it, a live **preview** shows the edit form exactly as authors will see it (under its groups' headings), and the
values as schema.org JSON-LD, built by the server from the unsaved draft (`POST /content/jsonld` with `draft`).
The draft's JSON stays available in the **JSON** tab. Save, Publish, "Try the editor" (the edit dialog on the newest
version) and Delete (while never published) are at the top. Everything goes through `DynamicFieldsClient`, so what a
user may do is what the API allows; its errors (403, 409 with the broken rule, ...) show as messages.

### The edit dialog

`Module.DynamicFields/edit-content` is the one generic editor for a node's values and style, opened by id through
`IModuleDialogs` (any client module can open it; a field's `editorDialog` names another to use instead):

```csharp
var result = await ModuleDialogs.ShowAsync("Module.DynamicFields/edit-content",
    new { field = "block.image", version = 2, content, style, nodeId, group }); // all but field are optional
if (!result.Canceled) { /* result.Data: { field, version, nodeId, content, style } */ }
```

The result always has a **node id**: the one given, else a new one (`n` and 12 hex digits). Keep it with the node: overlays
key on it. With `group` (a root field's value group, e.g. `seo`), the dialog shows only that group's values and no style,
checks only them, and returns the other values as they were given.

It loads the field version (the newest when none is given) and builds one control per value: text, a textarea for rich
text, number, checkbox, date, date and time, URL, a select (or checkboxes when multiple) for a choice, and a list with
Add and remove for multiple values. Style values are selects of the field's tokens; a responsive one can be set per
breakpoint. Save checks required values, then asks `POST /content/validate-node`, and shows each issue under its value.
Asset, Keyword and Term values are ids, with a Choose button when the user's catalog has a picker dialog for them
(parameters `{ multiple, selected, accept }`, result `{ ids, files? }`); without one, the id is typed:

- **Asset:** `Module.Media/pick-asset` when a media module is installed, else the Storage module's file browser,
  `Module.Storage/pick-files`, limited to the property's `accept` list. The chosen file shows by name, type and size
  (an image in a public folder as a thumbnail). The builder sets `accept` per Asset value, typed or with one click
  (Any file, Images, Video, Audio, Documents);
- **Keyword:** `Module.Keywords/pick-concepts`; **Term:** `Module.Taxonomies/pick-terms`.
Rich text is a plain textarea for now. The form itself is `ContentEditorForm`, which the builder's
preview also shows.

### Content translation

Content is written in one source language; each other language is an **overlay** kept beside it, never a copy of the
tree. Only textual values are translated: Text and RichText properties, unless the field says `translatable: false`
(a code, a slug). Ids, numbers, dates, choices, style and the tree's shape always come from the source, so a
translation can never break the content's structure.

```jsonc
{ "language": "en",
  "nodes": {
    "$root": { "headline": { "value": "Final day at the venue", "sourceHash": "3f0c9a1d2b7e4c55" } },
    "img1":  { "caption":  { "value": "The venue", "sourceHash": "91be0c7d4a2f1e08" } } } }
```

- **Keys:** the node id (`$root` for the root, which has none) and the property key, so overlays survive reordering
  and edits elsewhere in the tree. A child node needs a `nodeId` to be translated.
- **Staleness:** `sourceHash` is the hash of the source value a translation was made from. When the source changes, the
  value is *stale*: still served (unless `useStale: false`) and flagged for the translator until it is edited or
  marked still right.
- **Fallback:** a reader in `ar-EG` gets the `ar-EG` overlay, then `ar`, then the source, value by value.
- **Who keeps what:** this module owns the rules (`ContentTranslator` in Core: units, checks, merge, prune) and the
  editor; the consumer (Contents) stores one overlay per post and language, checks it with
  `POST /content/translations/check` before saving, prunes it after source edits, and serves readers through
  `POST /content/translations/apply` (or `ContentTranslator.Apply` when it references Core).

`Module.DynamicFields/translate-content` is the translation editor, opened by id like the edit dialog:

```csharp
var result = await ModuleDialogs.ShowAsync("Module.DynamicFields/translate-content",
    new { root, language = "en", translation, nodeId = "img1" }); // translation and nodeId are optional
if (!result.Canceled) { /* result.Data: the whole overlay { language, nodes }, checked by the server */ }
```

It shows each value's source beside an input in the target language (right to left for Arabic and the other RTL
languages), its state, "Copy the source" and "Still right" for a stale one. The field builder's "Try translating"
button opens it with the content the editor returned.

### JSON-LD

`JsonLdBuilder` (Core) turns a post into schema.org JSON-LD from its kind and each content's schema.org mapping;
`POST /content/jsonld` serves it, and the field builder's preview uses it. The request's `root` is the post with its
contents as children, in reading order. This module only has ids, so the caller sends what it knows about them: `assets`
(by id: `{ url, width?, height?, encodingFormat? }`, from Storage) and `names` (keyword concepts and taxonomy terms, by id);
`url` and `language` give `url`/`mainEntityOfPage` and `inLanguage`.

| Source | JSON-LD |
| --- | --- |
| The root's values | Under their schema.org property: an image file is an `ImageObject` (url, width, height), another file its url; a person (`author`, `editor`, ...) a `Person`, a publisher an `Organization`; `about`/`mentions` a `Thing`; a keyword or term its name; a lookup item its text; rich text plain text |
| An image content (`ImageObject`) | Added to `image`: an `ImageObject` with `contentUrl`, `url`, `width`, `height` and its own values (caption, credit, ...) |
| A video, an audio | `video`, `audio`: the object with `contentUrl`, size and its values |
| A gallery (`MediaGallery`) | Its images and videos, to `associatedMedia` |
| A quotation | `citation`: a `Quotation` (`spokenByCharacter` a `Person`) |
| Any other content | Its `text`/`headline` values to `articleBody` (`text` when the kind is not an Article), in reading order, a blank line between |

A value whose file or name is not given is left out, and so is a media content without its file; a node whose field
version is not published is left out and listed in `skipped`. `placeholders: true` shows what is empty as `‹label›`.

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.DynamicFields.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.DynamicFields.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.DynamicFields.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.DynamicFields.Web -ModuleId dynamicfields `
    -Output <this repo>/src/openapi/dynamicfields.json
```

## Installing

The server part is the build output of `WebApi.Modules.DynamicFields.Web` (`bin/<Configuration>/net10.0`: every layer
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: the tenant migrations run per tenant, the routes are mapped
under `/api/dynamicfields`.

The client parts are two assemblies, uploaded on the client's Client Modules page (`/client-modules`), the API client
first: `soft.square.net.WebApi.Modules.DynamicFields.Client.dll` (hidden; other client modules may depend on it) and
`soft.square.net.Module.DynamicFields.dll` (the Fields page). The playground builds all three for you: `playground/out/dynamicfields.zip`
and `playground/out/client/`.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.DynamicFields      this repo
```

(another location: `--property:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080,
client 5070), so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.DynamicFields.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart the `webapi` resource in the dashboard |
| `install` | The platform starts without the module, as in production; upload `playground/out/dynamicfields.zip` on http://localhost:5070/host-modules (sign in as the dev platform admin) and activate it, then the two dlls in `playground/out/client/` on http://localhost:5070/client-modules, the API client first |

In Development the platform seeds the tenants `acme` and `globex`. The playground grants the module's permissions in
`acme` to the dev accounts through `Access:DevGrants`: `acme-admin@modular.local` gets `dynamicfields.*`,
`editor@modular.local` gets `dynamicfields.read`. Their passwords are in the platform's
`WebApi.Identity.Server/appsettings.Development.json`. Sign in on http://localhost:5070 as `acme-admin@modular.local`
and open **Fields** for the Fields page; the API is browsable at http://localhost:5080/scalar.

Data stays in the Docker volume `dynamicfields-playground-data` and in `playground/.data`; delete both to start over.
